# Проверка масштабируемости: добавление шестого канала

Требование кейса: добавление источника снабжения должно поддерживаться через данные или
конфигурацию, без переделки расчётной логики.

## Что делали

В копию набора данных добавлена строка в `data/supply_sources.csv`:

```
F,Source-X,60,5.5,0.20,0.00,3,3,month,"constant:0.97",2036,TEAM_ASSUMPTION,"синтетический шестой канал"
```

Код не менялся. Запускались `npm test` и `npm run results`.

## Результат

| Показатель (стандартный сценарий) | Исходный набор (5 каналов) | С каналом Source-X (6 каналов) |
|---|---|---|
| Лучшая стратегия | ZBO 2036 + ISRU 2037 | ZBO 2036 + ISRU 2037 |
| Приведённые расходы | 8 715 млн у.е. | 8 317 млн у.е. |
| Расходы за горизонт | 10 578 млн у.е. | 10 071 млн у.е. |
| Стоимость тонны обслуженного спроса | 7,61 млн у.е./т | 7,25 млн у.е./т |
| Минимальный сервис | 100,0% | 100,0% |

Движок, проверки ограничений, подбор стратегий, реестр рисков и интерфейс подхватили новый канал
из данных: он попал в порядок распределения объёмов по стоимости тонны и вытеснил часть дорогих
поставок, снизив расходы.

## Что при этом падает намеренно

Три теста из `src/engine/__tests__` проверяют целостность исходного набора кейса: состав каналов
A–E (`engine.test.ts`), состав реестра рисков (`risks-export.test.ts`) и договорные карточки по
каналам (`contracts-kpi.test.ts`). При подмене данных они падают — это задумано: контрольное решение
кейса обязано считаться на исходных данных, а расширенный набор является отдельным исследовательским
сценарием. Прогон на изменённых данных: `Tests 3 failed | 112 passed (115)`.

После проверки строка Source-X удалена, обязательное решение кейса считается на исходных данных.
