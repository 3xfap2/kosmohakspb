# Топливный космоконтур 2035 — цифровой контур оператора

Прототип планирования снабжения орбитального топливного узла на 2035–2040 годы для кейса
«Топливный космоконтур 2035» (КосмоХакатон 2026). Оператор меняет решения по закупкам,
резервированию мощности, запасам и инвестициям и сразу видит материальный баланс, расходы,
обслуживание спроса, нарушения ограничений и сравнение стандартного и стрессового сценариев.

## Быстрый старт

```bash
npm install
npm run dev        # интерфейс на http://localhost:5173
npm test           # 115 проверок, включая контрольные примеры организатора V01–V10
npm run results    # пересчёт сохранённых планов и выгрузок в results/
npm run build      # продакшен-сборка в dist/
npm run preview    # просмотр собранной версии
```

Собранную версию нужно именно раздавать (`npm run preview` или любой статический сервер), а не
открывать `dist/index.html` файлом: в контексте `file://` браузер отключает `crypto.subtle`, и
регистрация со входом по паролю работать не будут. Гостевой вход работает в любом случае.

Внешние сервисы, ключи и платные подписки не нужны: все данные лежат в репозитории,
расчёт идёт в браузере. Секретов в репозитории нет.

## Что внутри

| Раздел | Что делает |
|---|---|
| Обзор | схема цепочки поставок, баланс по годам, запас по месяцам, ключевые показатели |
| План | редактирование заказов, резервирования и инвестиций с мгновенным пересчётом |
| Ограничения | проверки по набору организатора с годом, фактом, порогом и причиной |
| Сценарии | один план в стандартных и стрессовых условиях, перебор 36 стратегий, фронт Парето |
| Стресс-лаб | обратный стресс-тест, цена адаптации с учётом сроков поставки, чувствительность, расчёт за 2040 год |
| Риски | реестр с рассчитанными последствиями и Монте-Карло с фиксированным seed |
| Стороны | интересы участников, MCDA с раскрытыми весами и проверкой устойчивости выбора |
| Геополитика | конструктор условного события, причинная цепочка, сравнение до и после, выгрузка |
| Соответствие | карта критериев кейса: что проверяет жюри, где это в решении и какое доказательство открыть |
| Данные | выгрузки, ссылка на расчёт, сравнение двух планов, журнал решений с откатом |

Отдельно для проверки:

- **Ссылка на расчёт** — состояние плана, сценария и варианта спроса кодируется в адресе, проверяющий
  открывает ровно то, что показывали.
- **Трассировка числа** — на вкладке «Обзор» любой год раскрывается до формул, входов и правила
  организатора, по которому он посчитан.
- **Автосохранение работы** — план, сценарий и открытый раздел сохраняются в браузере: перезагрузка
  страницы или потеря связи не обнуляют разбор.
- **Журнал решений** — каждое изменение плана записывается и может быть откачено.
- **Панель тревог** — нарушения, показатели в красной зоне и приближение к порогам в одном месте.
- **Ассистент сбоку** — Ctrl+J: панель открывается поверх любого раздела. Вопрос на русском запускает
  расчёт в движке; в ответе указано, каким модулем получены числа.
- **Необязательный слой языковой модели.** Если в настройках ассистента ввести ключ OpenAI, ответ
  дополнительно формулируется моделью, но числа по-прежнему берутся из расчёта: модель получает
  готовый результат и не может его изменить. Ключ хранится только в браузере пользователя и в
  репозиторий не попадает; без ключа ассистент работает полностью офлайн.
- **Командная палитра** — Ctrl+K: переход по разделам, смена сценария, ссылка, печать.
- **Печать отчёта** — текущий раздел печатается или сохраняется в PDF со свежими числами.
- **Три темы оформления** — «Контур» (тёмный бирюзовый), «Полночь» (графит с тёплым акцентом) и
  «Бумага» (светлая, для проектора и печати). Палитра графиков для каждой темы проверена на контраст
  к фону карточек и различимость при дальтонизме.

Вход в рабочее место — через регистрацию или кнопку «Войти как гость»: учётные записи хранятся
в браузере, а гостевой доступ открывает все расчёты без регистрации, чтобы проверка не зависела
от чужих аккаунтов.

## Порядок проверки жюри

1. **Установка и запуск:** `npm install && npm run dev`, на стартовом экране — «Открыть рабочее место» и «Войти как гость».
2. **Стандартный сценарий:** вкладка «Обзор» — цепочка поставок, баланс и показатели по годам.
3. **Обязательный стресс:** переключатель «Стресс» в строке состояния; нарушения — на вкладке «Ограничения».
4. **Изменение решений:** вкладка «План» — правка объёмов, резервирования и инвестиций прямо в таблице.
5. **Дополнительные тесты:** «Стресс-лаб» — граница прочности, цена адаптации, чувствительность, расчёт за 2040 год; «Риски» — реестр и Монте-Карло с seed.
6. **Сравнение и выгрузка:** «Сценарии» — перебор стратегий и фронт Парето; «Стороны» — выбор глазами участников; «Геополитика» — условное событие; «Выгрузки» — CSV, JSON и повторное открытие плана.

## Структура

```
data/          исходные данные кейса (CASE_INPUT), скопированы из стартового репозитория без изменений
scenarios/     BASE и MANDATORY_STRESS в формате организатора
validation/    контрольные примеры V01–V10 и ожидаемые значения организатора
src/engine/    расчётное ядро без интерфейса: модель, ограничения, стратегии, риски, стресс-лаборатория,
               многокритериальный выбор, геополитические сценарии, ассистент
src/ui/        интерфейс: посадочная страница, вход, разделы рабочего места, графики
tools/         генератор сохранённых расчётов
results/       сохранённые планы, выгрузки и сводка (npm run results)
docs/          записка, протоколы, источники, сценарий показа, скриншоты
```

Расчёт отделён от интерфейса: в `src/engine` нет ни одного импорта React, поэтому ядро
проверяется тестами и запускается скриптом без браузера.

## Откуда берутся числа

| Статус | Что это | Где лежит |
|---|---|---|
| `CASE_INPUT` | спрос, каналы, хранилище, инвестиции, ограничения, сценарии | `data/*.csv`, `scenarios/*.yaml` — читаются как есть, значения не переписаны в коде |
| `TEAM_DECISION` | объёмы заказа, резервирование мощности, инвестиции, начальный запас | `Plan.decisions`, формат совместим с `schemas/plan.schema.json` организатора |
| `TEAM_ASSUMPTION` | ставка дисконтирования, политика диапазонов lead time, определение базового канала, правило «заказ ≤ резерв», равномерность внутри года | `Plan.assumptions`, показаны на вкладке «План» |

## Контрольные правила и где они реализованы

| Правило организатора | Реализация | Проверка |
|---|---|---|
| `I_end = I_start + Q_delivered − Losses − Q_served` | `closingInventory` | V01, помесячная проверка на данных кейса |
| Дефицит отдельно, отрицательного запаса нет | `serve` | V02 |
| `Q_pay = max(Q_order, take_or_pay × Q_reserved)`, без второго начисления | `payableVolume` | V03, V04 |
| Плата за резервирование пропорциональна периоду | `reservationPayment` | V05 |
| Потери один раз на валовое поступление | `losses` | V06 |
| `R_y = D_y × 45 / 365` | `reserveRequirement` | V07 |
| Резерв не больше мощности канала | `capacityCheck` | V08 |
| Критический спрос вложен в общий | `demandFor` | V09 |
| Доли поставки стресса не умножаются на надёжность | `actualDelivery` | V10 |
| Надёжность — только в риск-блоке | `risks.ts` | тесты риск-блока |

## Модель

- **Шаг — месяц.** Он выявляет внутригодовой дефицит и переполнение хранилища и позволяет
  пропорционально начислять плату за резервирование и хранение.
- **Сроки поставки** применяются там, где канал вводится внутри горизонта: Earth-New получает
  подготовку 18–24 месяца после исполнения опциона, Lunar-ISRU — 1–2 месяца после ввода, поэтому
  в первый рабочий год доступна не вся его мощность. Для каналов, доступных с 2035 года
  (Earth-Core, Earth-Flex, Emergency), заказ размещается в подготовительном периоде до начала
  горизонта — это допущение команды, и из-за него их lead time не ограничивает плановый график.
  На скорость реакции эти сроки влияют: она считается в разделе «Цена адаптации».
- **Разделение сущностей.** Зарезервированная мощность, заказанный объём, фактическая поставка и
  выданный потребителям объём считаются отдельно и нигде не складываются.
- **Критический спрос обслуживается первым**, входит в общий и не прибавляется к нему повторно.
- **Платежи.** Закупка считается по оплачиваемому объёму (take-or-pay внутри `max`), резервирование —
  по годовой ставке с пропорцией, хранение — по среднему физическому запасу с учётом времени.
- **Ограничения** читаются из `data/constraints.csv` вместе с идентификаторами: требования сервиса,
  лимиты CAPEX, 45-дневный резерв, роль Emergency, предел потерь в стрессе.

## Масштабируемость

Добавление шестого канала снабжения делается строкой в `data/supply_sources.csv`: материальный баланс,
распределение объёмов, проверки ограничений, подбор стратегий и выгрузки перебирают источники из данных.
Проверка воспроизводится и описана в `results/extensibility_check.md`. Оговорка: часть блоков всё же
адресует каналы по идентификатору — привязка инвестиций к Earth-New и Lunar-ISRU, ограничение на роль
Emergency, реестр рисков и сетка чувствительности. Новый канал они подхватывают как обычный источник,
но специальных правил для него не создают. Расширение горизонта — строками в `data/demand.csv`.
Формулы при этом не меняются.

## Ограничения прототипа

- Годовой объём распределяется по месяцам равномерно; неравномерный график поставок не моделируется.
- Диапазоны lead time (18–24 месяца у Earth-New, 1–2 месяца у ISRU) сводятся к одному значению по
  раскрытой политике, а не моделируются интервалом.
- Сроки поставки каналов, доступных с 2035 года, не ограничивают плановый график: предполагается,
  что заказ размещён в подготовительном периоде. Подготовительный период отдельным расчётом не
  моделируется — в нём считается только начальный запас.
- Монте-Карло предполагает независимые отказы каналов — это допущение, а не установленный факт.
- Стоимость срыва миссии и выручка не считаются: организатор их не задаёт.
- Промышленное развёртывание, интеграция с оборудованием и круглосуточный сервис не предусмотрены.

## Документы

- `docs/УПРАВЛЕНЧЕСКАЯ_ЗАПИСКА.md` — архитектура расчёта, стратегия и экономика, контракты, дорожная
  карта и роли, KPI, стресс-тесты, риски, интересы сторон, геополитический блок, горизонт за 2040 год.
- `docs/РЕЗЮМЕ_СЦЕНАРИЕВ.md` — одностраничное сравнение сценариев с обоснованием сохранённых решений.
- `docs/ПРОТОКОЛЫ_ТЕСТОВ.md` — протоколы всех проверок: вход, ожидаемое, фактическое, воспроизведение.
- `docs/ИСТОЧНИКИ.md` — источники с DOI и связью «источник → метод → реализация → граница применимости».
- `docs/ДЕМО_СЦЕНАРИЙ.md` — показ контура за три минуты: что нажимать и что говорить.
- `docs/ВОПРОСЫ_И_ОТВЕТЫ.md` — вероятные вопросы жюри, ответы и разделы контура, где это видно.
- `docs/screenshots/` — снимки всех экранов в теме «Контур».
- `results/summary.md` — сводка чисел, совпадающая с интерфейсом и выгрузками.
- `results/extensibility_check.md` — протокол добавления шестого канала через данные.

В `results/` лежат прогоны всех четырёх сценариев (стандартный, стресс, низкий и высокий спрос),
реестры рисков, договоры, KPI, обратный стресс-тест, адаптация, геополитика, минимакс сожалений и
многокритериальный выбор — всё в CSV плюс полные конверты в JSON.
